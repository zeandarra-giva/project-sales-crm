Complete Request Lifecycle — "List Deals"
This is what happens when a user opens the Pipeline page. Understanding this one flow means you understand every flow — the pattern is identical for clients, contacts, and everything else you'll build.
GET /api/deals — Step by Step
1
User navigates to /pipeline
React Router renders Pipeline.tsx. This page component mounts and needs deal data.
frontend/src/pages/Pipeline.tsx
2
Hook fires React Query
The page calls useDeals() or uses useQuery({ queryKey: ['deals'], queryFn: getDeals }). React Query checks its cache — if stale or empty, it calls the query function.
frontend/src/hooks/useDeals.ts
3
API function calls Axios
getDeals() calls api.get('/api/deals'). The Axios instance automatically attaches the JWT token from authStore to the Authorization: Bearer ... header.
frontend/src/api/deals.ts → frontend/src/api/client.ts
4
HTTP request hits Motia server
Vite's dev proxy forwards /api/* to localhost:3111. Motia routes the request to the matching step handler based on the URL path and method.
steps/api/deals/list.step.ts
5
Step handler authenticates + queries
The step calls authenticate(req) which verifies the JWT. Then it queries Prisma: prisma.deal.findMany() with include to join related tables (client, stage, BD). If user is BD_REP, it filters to only their deals.
lib/auth.ts → lib/db.ts
6
Prisma queries PostgreSQL
Prisma translates the query to SQL, sends it to PostgreSQL, and returns typed JavaScript objects. Related data (client name, stage info) comes back already joined.
prisma/schema.prisma
7
Response flows back to browser
Step handler formats the data and returns JSON with status 200. Axios receives it, React Query caches it and triggers a re-render of the Pipeline page.
8
UI renders deals
PipelineBoard groups deals by stage and renders DealCard for each. Data is reactive — any mutation (like creating a deal) invalidates the cache and refetches automatically.
frontend/src/components/deals/PipelineBoard.tsx
Create Flow — "Add New Deal"
POST /api/deals — Step by Step
1
User fills out DealForm and submits
React Hook Form validates the input on the client side. On submit, it calls a mutation function.
frontend/src/components/deals/DealForm.tsx
2
useMutation sends POST
TanStack Query's useMutation calls createDeal(payload). Axios POSTs to /api/deals with the form data as JSON body + JWT header.
frontend/src/api/deals.ts
3
Backend validates with Zod
The create step handler authenticates the request, then validates the body against a Zod schema. If invalid, returns 400 with validation errors. If valid, proceeds to create.
steps/api/deals/create.step.ts
4
Prisma creates record + returns with relations
prisma.deal.create() inserts the row and uses include to return the deal with its client, stage, and BD info already joined.
5
Cache invalidation triggers refetch
On mutation success, queryClient.invalidateQueries(['deals']) marks the deals cache as stale. React Query automatically refetches, and the pipeline UI updates to show the new deal.
The Pattern For Every CRUD Operation
Key insight: Every feature you'll build follows the exact same pattern. The only things that change are the model name, URL path, and fields. The architecture stays identical.

Page → Hook (useQuery/useMutation) → API function → Axios + JWT → Step handler → Zod validation → Prisma query → PostgreSQL

When you build Client CRUD, you'll create: steps/api/clients/list.step.ts, create.step.ts, update.step.ts — each following the same structure as the existing deal steps. Then wire up frontend/src/api/clients.ts and the hooks.
Core Entities — What You'll CRUD
Mental model: Think of your database in three tiers. Core entities are what users interact with directly (deals, clients, contacts). Dimension tables are reference data that rarely changes (stages, industries, services). Event/Analytics tables track history and metrics (audit logs, snapshots, forecasts).
Deal
The central fact table — everything revolves around this
PK id
FK bdId → BD (who owns this deal)
FK clientId → Client (the company)
FK stageId → PipelineStage (where in funnel)
FK serviceId → Service (optional)
FK bundleId → Bundle (optional)
+ dealName, revenue, duration, leadSource, dates, remarks…
Client
Companies you're selling to
PK id
FK industryId → Industry
FK contactId → Contact (primary)
FK referralId → Client (self-ref)
+ name, brand, accountType, status
Contact
People at client companies
PK id
FK clientId → Client
+ firstName, lastName, email, designation, decisionRank, isPrimary
BD (Sales Rep)
Your team members — also the auth users
PK id
+ firstName, lastName, email, password, role (BD_REP | SALES_MANAGER)
How Entities Relate
Core Relationships (what you need for CRUD)
BD ——1:N——▸ Deal A BD rep owns many deals
Client ——1:N——▸ Deal A client can have many deals
Client ——1:N——▸ Contact A client has many contacts
PipelineStage ——1:N——▸ Deal A stage has many deals in it
Deal ——N:M——▸ Contact via DealContact junction table
Analytics Relationships (for later — dashboards & reports)
Deal ——1:N——▸ DealAuditLog Every stage change is logged
Deal ——1:1——▸ DealProjection Win probability forecast
BD ——1:N——▸ Target Quota records per period
Deal ——1:N——▸ DealSnapshot Point-in-time state captures
Deal ——1:N——▸ Payment Monthly payment records
Dimension / Reference Tables
PipelineStage
7 stages: Inquiry → Prospecting → Discovery → Proposal Sent → Negotiation → Closed Won / Lost
name (unique), duration (target days in stage)
Industry
Hierarchical industry list (self-referencing for sub-industries)
Service + Bundle
Service catalog with bundling support (many-to-many via BundleService)
DateDimension
Time dimension for analytics — year, month, quarter, dayOfWeek, isQuarterEnd
Authentication Flow — Login to Protected Request
1. Login Flow
1
User enters email + password on Login page
Login.tsx calls authStore.login(email, password)
frontend/src/pages/Login.tsx → frontend/src/store/authStore.ts
2
POST /api/auth/login
Backend finds BD by email, compares bcrypt hash of password. If match, signs a JWT: { bdId, email, role, exp: 24h }
steps/api/auth/login.step.ts → lib/auth.ts
3
Token + user stored in Zustand
authStore saves { token, user, isAuthenticated: true }. Zustand's persist middleware writes this to localStorage['crm-auth'] so it survives page refresh.
4
Redirect to /dashboard
React Router navigates to the dashboard. All subsequent API calls include the JWT.
2. Protected Request (every API call after login)
1
Axios interceptor attaches token
Before every request, the Axios request interceptor reads authStore.token and sets Authorization: Bearer <token>
frontend/src/api/client.ts
2
Backend verifies JWT
Step handler calls authenticate(req): extracts token from header → jwt.verify() → fetches BD from DB → checks isActive. Returns user object or throws 401.
lib/auth.ts
3
If 401 → automatic logout
Axios response interceptor catches 401 errors → calls authStore.logout() → clears token + user → redirects to /login.
3. Route Protection (AuthGuard)
1
AuthGuard wraps protected routes
In App.tsx, routes like /pipeline are wrapped: <AuthGuard><Pipeline /></AuthGuard>
2
Checks token + validates with server
On mount, AuthGuard checks if token exists in authStore. If yes, calls GET /api/auth/me to verify it's still valid. If no token or server rejects → redirect to login.
3
Role check (optional)
AuthGuard accepts a requiredRole prop. Executive dashboard uses <AuthGuard requiredRole="SALES_MANAGER"> to block BD reps.
Recommended Build Order
Suggested order: Build in this sequence because each step gives you something the next step needs. Clients first (standalone), then Contacts (depend on Client), then complete Deal CRUD (depends on both).

For each entity, follow the same pattern:
1. Create the step handler files (backend)
2. Wire up the API functions (frontend/src/api/)
3. Update the hooks to use real API instead of mock
4. Test with the existing frontend pages
